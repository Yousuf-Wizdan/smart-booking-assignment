Step 1 Sign in public

Register creates an employee account and stores its token automatically. Use that token for everything below.

POST /api/v1/auth/register

Create an employee account. Public — no token needed. The returned token is saved and shown in the header.

POST /api/v1/auth/login

Sign in with an existing account. Public. Replaces the stored token.

GET /api/v1/auth/me

Show who the current token belongs to: username, role and employee id.

Step 2 Evaluate & book EMPLOYEE | ADMIN | APPROVER

Always Evaluate first — it is a free dry-run that shows the decision and every rule's verdict. Then Create to save the booking. New ids auto-fill the lookup forms below.

POST /api/v1/bookings/evaluate?explain=

Dry-run the rule stack without saving anything. Returns ALLOW, DENY or NEEDS_APPROVAL plus a per-rule breakdown. Non-admins: leave employeeId empty — the server uses your own account.

POST /api/v1/bookings

Save a real booking. Runs the same rules as Evaluate. The new booking id fills the Get / Cancel / Explanation forms automatically.

GET /api/v1/bookings/{id}

Fetch one booking by its id.

GET /api/v1/bookings

Search bookings. Every filter is optional — leave all empty to list everything.

POST /api/v1/bookings/{id}/cancel

Cancel a booking. Its seat goes back to the cost-centre quota.

GET /api/v1/bookings/{id}/explanation

Show the stored rule-by-rule reasoning for an existing booking — which rules ran, in what order, and why each passed or failed.

Employees

Reading needs any signed-in role. Creating and editing need ADMIN.

POST /api/v1/employees ADMIN

Add an employee record directly (admin only). Prefer Register for normal sign-ups.

GET /api/v1/employees/{id}

Fetch one employee by id.

GET /api/v1/employees

List employees, paged.

PUT /api/v1/employees/{id} ADMIN

Replace an employee. Full replacement — every field below is required.

Step 3 Approvals APPROVER | ADMIN

Bookings decided as NEEDS_APPROVAL wait here until approved or rejected.

GET /api/v1/approvals/pending

List bookings waiting for a decision.

POST /api/v1/approvals/{bookingId}/approve

Approve a pending booking — it becomes CONFIRMED and takes a quota seat.

POST /api/v1/approvals/{bookingId}/reject

Reject a pending booking — terminal, frees any held seat.

Quotas ADMIN

A quota is the seat pool for one cost centre. Bookings consume seats; cancellations return them.

GET /api/v1/quotas

List all quotas with capacity, reserved and free seats.

POST /api/v1/quotas

Create a seat pool for a cost centre.

PUT /api/v1/quotas/{id}

Change capacity. reservedSeats is an optional manual correction (0 … capacity).

Policies ADMIN

The rule stack. Blank business unit / cost centre means "applies to everyone". Lower priority number runs first. Toggle or reorder rules with the PATCH forms - no redeploy needed.

GET /api/v1/policies

List every rule with its scope, priority, on/off state and parameters.

POST /api/v1/policies

Add a rule. Parameters depend on the type: BOOKING_CUTOFF takes {"cutoffMinutes":60}, NIGHT_SAFETY takes {"nightStart":"22:00","nightEnd":"05:00","requireEscort":true}, others take {}.

GET /api/v1/policies/{id}

Fetch one rule by id.

PUT /api/v1/policies/{id}

Replace a rule wholesale — same fields as Create.

PATCH /api/v1/policies/{id}/enabled

Switch a rule on/off without touching anything else. Use this to demo “change rules without a redeploy”.

PATCH /api/v1/policies/{id}/priority

Reorder a rule without touching anything else.
